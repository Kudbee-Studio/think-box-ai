## 1. Audit (the state before this PR; from reading the code, then proven by the tests below)

**Verdict: there was one engine and one database, not two.** The CLI and the dashboard both used `server.ts` / `AgentSession`, `apps/web/data/think-tokens.db`, the same memory directory and the same ranker. What was wrong:

| # | Mismatch | Effect |
|---|---|---|
| M1 | Each WebSocket connection is its own session and `broadcast()` writes only to that session's socket | A goal run from the CLI appeared in run history (`/api/runs`, global) but **not live in the dashboard terminal** |
| M2 | The CLI had no identity: it only sent an `Origin` header that any local process can set | no authentication, and no way to label or mirror CLI runs |
| M3 | `KUDBEE_URL` could point anywhere | the CLI would talk to a non-local server |
| M4 | The CLI default `http://localhost:3000` while the server listens on `127.0.0.1` | works through name resolution, but is an avoidable ambiguity |
| M5 | Server down: the CLI started the server silently ("Starting...") | not wrong (same engine), but unannounced |
| M6 | Command drift: 10 CLI-only and 13 dashboard-only slash commands, no map, no test | silent divergence |

## 2. What changed

- **Live link (M1, M2):** the server creates a random token in `<data dir>/.kudbee-token` (mode 0600). The CLI reads it and sends it on the WebSocket upgrade (`x-kudbee-token`); the server refuses a wrong token, treats a valid one as `client: cli`, and relays that session's thoughts, results, queue and run updates to dashboards that sent `subscribe_runs` as labeled `mirror` messages (`[cli 694f1507] ...`). Approval requests are never relayed. The dashboard terminal renders them as labeled lines and refreshes run history. The token is never printed, logged or sent to a dashboard (tested). The server still listens on 127.0.0.1 only and still checks Host and Origin.
- **Loopback only (M3, M4):** the CLI refuses a `KUDBEE_URL` that is not 127.0.0.1/localhost/::1 and now defaults to `http://127.0.0.1:3000`.
- **Server down (M5):** the CLI says so and starts the **same** server (same data directory) on 127.0.0.1, then talks to it like any client; it stays up. This is not "in-process": `server.ts` boots HTTP, WebSocket, the database, memory and the model loader, so an in-process copy would be the second engine this PR exists to remove. If you want a literal in-process mode, that needs the engine split out of `server.ts` first.
- **Commands (M6):** `/tokens`, `/lessons` (same thing) and `/token TT-id` now exist in **both** the CLI and the dashboard terminal (the latter opens the Think Tokens view with the search or id typed in); `kudbee run "<goal>"` works like `kudbee "<goal>"`.
- **Parity map and test** (`apps/web/command-parity.ts`, `tests/command-parity.test.ts`): every slash command on either surface must be declared (both / counterpart view / surface-only / gap); counterparts must exist in the other side's source; the named capabilities (run, tokens list/show/links, lessons, memory, status, run history) must exist on both; the gap count may only shrink. Mutation check: adding an undeclared command makes it fail. **11 real gaps remain** and are listed, not hidden: `/skills`, `/skill` (CLI only); `/capacity`, `/config`, `/export`, `/logs`, `/plugin`, `/remote`, `/session`, `/sessions`, `/specialists` (dashboard terminal only).
