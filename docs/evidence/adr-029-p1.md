# ADR 029 P1 + P2 — evidence

Date: 2026-10-01. Scope: Think Token lifecycle with permanent `TT-` ids, a real extractor and challenge, a score breakdown, the CLI/dashboard
shared reader, the merged Think Tokens view, real-event cube pulses and an Energy Core. P1 and P2 shipped in one PR to save CI runs.

State words: CODE COMPLETE / TEST VERIFIED / LIVE VERIFIED / PRODUCTION READY, plus UNPROVEN. A state is the highest one with evidence; it never
implies the ones above it. **Nothing here is PRODUCTION READY.** LIVE VERIFIED below means a real run on the real server with the real model
(Mercury 2); mocks, seeds and timer events were not counted. The raw output is in `docs/evidence/adr-029-p1/`, screenshots in
`docs/screenshots/think-tokens-p1/`.

## 1. How the live proof was run

- Real `apps/web/server.ts` on `127.0.0.1:3001`, real Mercury 2 (`INCEPTION_API_KEY` for the worker, `INCEPTION_API_KEY_2` for extraction and challenge,
  both loaded from the repo `.env`; the values were never printed). The vector store was pointed at a dead address so nothing wrote to an external service.
- Database: a consistent copy (`VACUUM INTO`) of the real `apps/web/data/think-tokens.db` (4 legacy `tt_<hash>` candidate rows on schema v1), so the real data
  was migrated without touching the original file.
- Goals were submitted through the real CLI (`KUDBEE_URL=http://127.0.0.1:3001 kudbee --yes "<goal>"`) and, for the browser check, through the real dashboard
  UI in Windows Chrome (headless, throwaway profile, driving the real page in an iframe). The local Ollama model was **not** reachable (`ollama` is not installed in
  this environment), so only the Mercury path is LIVE.
- Cost: 4 CLI runs and 3 UI runs of small goals, about 19 successful Mercury extraction/challenge calls (8,268 tokens in, 7,034 out) plus the worker runs.

## 5. Challenge pass (trying to break each claim)

| Attack | Result |
|---|---|
| Duplicate content | returns the existing id, `seen_count` +1, no new number consumed (tested) |
| Restart | ids continue after reopening the file; ledger verifies (tested; live server restarted 3 times on the same DB) |
| Retire / reject / hard `DELETE`, then create | next id is higher; a number is never reissued (tested) |
| Concurrent writers | 4 processes x 25 writes: 100 distinct gap-free ids (tested) |
| Illegal transition (skip a step, accept without a passing challenge, pipeline retire, template advance, repeat a step) | refused and receipted as `rejected` (tested) |
| Forged `think_token_learned` / `_used` from a client | the server answers "Unknown message type"; nothing broadcast; counts unchanged (live) |
| Forged / SQL-shaped / oversized `run_id`, query of 200,000 chars, `TT-0`, an id with SQL, an extra `permissions` key, a bad status, non-JSON | each refused at the door with a specific error; no ledger entry, no row (live) |
| A well-formed `run_id` that matches no run | returns an empty list, creates nothing (live) |
| Event with no database row | cannot happen: the server builds events from a stored row (`tokenEvent(row, ...)`); the browser ignores any event that fails its schema (tested: 16 malformed shapes) |
| Token text containing HTML or script | rendered with `textContent`; no element is created; never reaches `innerHTML` (tested) |
| Secret in run output | redacted by the admission gate; prompts to Mercury have secrets and absolute paths removed and are size-capped (tested) |
| A hostile upstream error that echoes the key | scrubbed before it reaches the ledger or any message (tested; mutation below) |
| Missing `INCEPTION_API_KEY_2` | no Mercury caller; local model, else labeled template (tested) |
| Mercury returns an empty body once | retried once inside the per-run cap (tested; seen live) |
| Mercury answers with unusable text | nothing is saved and no template fallback; a sanitized excerpt is receipted (tested; seen live) |
| Model call caps | per-run (default 10) and per-day (default 200) caps stop calls and are receipted (tested) |
| `prefers-reduced-motion` | no cube twist, longer plain highlight, Energy Core animation off (tested as code and CSS; **not** exercised in a real browser) |
| A lesson that merely paraphrases a saved one | saved lessons are shown to the extractor and the challenge must say `novel`; a missing answer leaves the token unchallenged (tested; **the `novel: false` rejection was never observed live**) |

**Mutation checks** (a test is only trusted if it fails when the protection is removed): disabling `scrubSecrets` made the key test fail, and restoring it made it pass.

## 6. What could be fake — and the check that rules each out

| Way the UI could show something not backed by data | Check |
|---|---|
| A token card that is not in the database | cards are built only from the `think_tokens` message the server fills from `readTokens(store, ...)`; the CLI reads the same file; parity JSON test; a malformed list is ignored |
| A counter that was typed in, not measured | every count is labeled by source: "N shown from SQLite", ledger entries from `verifyLedger()`; Energy Core says "real signals from this browser session only" |
| Timer-generated activity | the only timer in the view is a 1 s repaint that never dispatches events; a test asserts the script contains no `dispatchEvent`; the Energy Core reads zero when idle (tested, seen in the idle screenshot) |
| A cube pulse with no token behind it | pulses fire only on `think_token_learned/used`, which the server emits from a stored row; clients cannot inject them (live) |
| A lesson that merely looks model-written | the row stores `extractor`, `extract_model`, `challenge_model`; template tokens are labeled "not model-written" and cannot advance |
| A token accepted without a challenge | `advance(.., 'accepted')` refuses unless `challenge_verdict = 'pass'` and a `challenge_model` exists (tested) |
| A fabricated "used by" or reuse | `think_token_uses` rows are written by `recordUse` when the planner is handed the token; the dashboard reads them back |
| A score that is only a label | the breakdown is stored in the database and recomputed on every use; the CLI prints components x weights = total |
| A browser check run on a mock | the live runs used the real server, the real database copy and real Mercury 2; the earlier harness screenshots are separately labeled synthetic |
| "Identical in CLI and dashboard" by construction | one `toApiToken`; the test compares real outputs of two separate processes |
| Evidence containing the key | scanned: 0 occurrences of the real value in every artifact and table |

## 7. Findings from running it (what the evidence ledger caught)

1. **A transient Mercury failure stranded a good lesson.** `TT-000007` stayed at `scored` because one challenge call returned an empty body (receipted:
   `mercury returned no text`) and the local model was unreachable. Fixed: one Mercury retry inside the per-run cap. `TT-000007` itself was not re-challenged
   (there is no mechanism that revisits `scored` tokens): **known gap**.
2. **The challenge did not discriminate.** Mercury passed 12 of 12 lessons it was asked about, and many accepted lessons are paraphrases of each other (six variants
   of "write_file, then confirm with list_files"). Keyword overlap between paraphrases tops out at 0.28 against a median of 0.07 for unrelated lessons, so a
   similarity threshold would be unreliable. Fixed in a different way: saved lessons for the same goal and tools are given to the extractor and the challenge,
   and the reviewer must say whether the lesson is new. A later live run, handed three known lessons, found nothing new and saved nothing.
   **Whether the challenge can actually reject a bad lesson is still UNPROVEN live.**
3. **A model that answered "nothing new" triggered a template fallback** (`TT-000018`, a candidate that says only "this tool sequence worked"). Fixed: a model that
   answered, even unusably, saves nothing; the run now says "No new Think Token from this run".
4. **The Energy Core read "idle" in the first screenshot** because Chrome fast-forwarded its clock after the script ended and the 30 s decay fired. The live samples
   show it `active`; the capture was retaken with a short virtual-time budget. Recorded because the decay is a real behavior, not a rendering fault.
5. **A harness mistake, not a product bug:** the first "jump to TT-5" check came back empty because the driver held virtual time and the 250 ms debounce could not fire;
   with the driver fixed the jump highlighted `TT-000005`.

## 10. UNPROVEN

- The local Ollama fallback against a real local model.
- That the challenge can reject a poor lesson: every live lesson it saw passed (12 of 12), and the `novel: false` path was only exercised with fakes.
- Learning quality in general: whether accepted lessons make later runs better. Reuse is recorded and scores move, but no run's outcome was compared with and without a token.
- `prefers-reduced-motion` in a real browser; the cube pulse animation visually (the live runs verified the events and the view, and the screenshots were taken after the pulses ended).
- The per-run and per-day call caps against real Mercury.
- Real-device touch and screen readers.
- Revisiting `scored` tokens, heat-map mode, the six-face mapping, Disruption Tokens, long-range connections (P3-P5).

## 11. Privacy and limits

Prompts for Mercury 2 leave the machine. The run record is sanitized first (secrets and absolute paths removed, text capped at 8,000 characters), but the redaction is
best-effort. Lessons are advisory text and grant no permission, tool or approval; planner use is still gated by the normal approval modal.
