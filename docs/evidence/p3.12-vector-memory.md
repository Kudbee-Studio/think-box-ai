# P3.12: local vector memory (SQLite, no Upstash) and the live-run fixes (2026-10-02)

Mercury spend: about **$0.03** of the $0.10 cap (two live runs on :3000, one CLI run). The real database was backed up before any write (`think-tokens.db.bak-pre-p312-20261002`, and the migration made `.bak-pre-v5-20261002`; the memory folder was copied to `data/memory-backups/memory-pre-p312`). All local and gitignored.

## 1. Audit of the memory store (before this change)

| Question | Answer |
|---|---|
| Where memories live | Markdown files with front matter in `<data dir>/memory/{task,org,verified}` (`apps/web/data/memory`); the files are the source of truth, `MemoryStore` (`memory.ts`) mirrors them in RAM |
| How recall ranked | an in-process BM25 (`localSearch`); title and tags count twice |
| Where Upstash was wired | `memory.ts`: any `UPSTASH_VECTOR_REST_URL` + `UPSTASH_VECTOR_REST_TOKEN` switched the store to the `upstash-sparse` backend (sparse BM25-style term vectors computed locally, sent to Upstash; not a semantic embedding), `syncVectors()` ran at boot, `write`/`remove` upserted, `search` merged remote and local hits; a monitor entry in `server.ts` probed it. The repo `.env` sets both variables, which is why every recall said `hybrid (upstash-sparse + local-bm25)` or, when unreachable, `local-bm25 (vector offline)` |
| Env vars | `UPSTASH_VECTOR_REST_URL`, `UPSTASH_VECTOR_REST_TOKEN`, `KUDBEE_VECTOR_NAMESPACE`; memory dir `KUDBEE_MEMORY_DIR` |

**Found during this work:** the first version of the opt-in still let the boot-time `syncVectors()` call Upstash whenever the variables were set (the live recall still said `upstash-sparse`). Fixed, with a test that fails if the startup sync contacts the service without the opt-in.

## 2. What changed

- **Local vectors:** every memory is embedded with the already-loaded `Xenova/all-MiniLM-L6-v2` (task episodes without their unverified answer) and stored in SQLite, table `memory_embeddings` in `think-tokens.db` (schema v5; an automatic `.bak-pre-v5-<date>` copy is written before the migration). A memory is re-embedded only when the sha256 of its text changes; vectors of deleted memories are pruned. The first recall backfills everything (53 memories embedded on your real data).
- **Recall rule (fixed before the eval, as for tokens in P3.8):** cosine first (floor 0.15, buckets of 0.02), BM25 only breaks ties inside a bucket, BM25-only matches (an exact keyword the model scored low) follow. The superseded filter and the duplicate collapse from P3.10 stay.
- **Labels in the thought stream:** `local-vector (MiniLM)`, or `local-bm25 (model loading)` / `(embeddings off)` / `(embedding model failed to load: ...)`, or plain `local-bm25` when there is no provider.
- **Upstash is opt-in only:** nothing contacts it (recall, writes, the boot sync, the monitor probe) unless `KUDBEE_MEMORY_BACKEND=upstash` is set with its URL and token. The adapter is not deleted.

## 3. Eval: BM25 vs local vectors (hermetic corpus, one run, no tuning)

`scripts/memory-recall-eval.mjs`; corpus of 20 memories and 10 paraphrased queries (each shares at most one distinctive word with its expected memory; tested) committed in `31608764` before the run; raw `adr-029-p3/p312-memory-recall-eval.json`.

| Ranker | hit@1 | hit@3 |
|---|---|---|
| BM25 (previous default, `local-bm25`) | 2 / 10 | 2 / 10 |
| **local vectors (`local-vector (MiniLM)`)** | **8 / 10** | **10 / 10** |

Misses at rank 1: `q7` (lesson identifiers recycled? found at rank 2 behind the token-lifecycle memory) and `q10` ("the list of proposals under review" found at rank 3). The corpus is written by one author, small, and not the founder's real memories; BM25 is weak on paraphrases by construction. Evidence of direction, not a benchmark.

## 5. Fixes from the live CLI run (same PR)

| | Problem | Fix | Test |
|---|---|---|---|
| (a) | The model guessed `kudbEE/kudbEE` and got a 404 | `KUDBEE_REPO` (else read from `git remote get-url origin`) is injected into the planner context as a KNOWN REPOSITORY line (`repo-context.ts`) | URL parsing, env override, git remote of this checkout; a real-server CLI run asserts the line is in the system prompt |
| (b) | The evidence check flagged a correct answer because an earlier call 404'd although a later page supported it | a failed or empty result is **superseded** when a later result succeeded: it no longer makes an answer a conflict candidate, and the judge is told to judge against all results in order, shown `superseded_by_later_success` per result, and that a later success outranks an earlier failure | built from this exact trace (7 tool results, the real answer); mutation check: removing the supersede logic fails the test; an agent-level replay checks the judge payload and that no retry happens |
| (c) | `list_files` returned nothing, then `read_file pr_status.md` on a guessed name | a planner rule, plus a guard: after an empty `list_files` (and nothing written since) `read_file` on a path this run has not written returns a clear error instead of touching the file system | replay; mutation check; reading works after the file is written; a non-empty workspace is unaffected |
| (d) | "qwen2.5:1.5b not found" on every run | no warning at all when no Ollama model is installed; when Ollama has models but the configured one is missing, one warning per 24 h (marker in `~/.kudbee`) that names the installed models; the per-goal "💡 ... not installed" line is shown only with `KUDBEE_VERBOSE=1` | real-server CLI runs print no warning and create no marker; the Ollama-present, model-missing branch is **not tested** (no fake Ollama) |
| (e) | The final answer after the retry was not printed | the CLI always prints the final answer (or a plain "(no answer)"/error text) and, when the evidence check fired, a line saying the first answer conflicted; the server now includes `evidence_conflicts` in the result | real-server CLI run: the corrected answer is printed after a retry. I could not reproduce the founder's missing-answer output (the CLI printed it in every run I made); this change makes the print unconditional |
